# Google Drive synchronization contract

The canonical OpenAPI document is generated by FastAPI at `/openapi.json` (Swagger UI: `/docs`). This repository has no checked-in OpenAPI source or generated client; route and Pydantic declarations are the source of truth.

## Transfer boundary

The Flutter app owns snapshot creation, validation, compression, optional encryption, hashing, direct Drive API upload/download, Drive-side conditional writes/deletes, version comparison, conflict prompts, merge, and local transactional restore. No Noema route accepts or returns backup bytes. The backend stores only app-declared, bounded metadata and safe synchronization events. A declared hash or size is not verified by Noema.

For direct Drive writes, the app must use the Drive API revision/ETag precondition (`If-Match` where supported) in addition to the Noema metadata precondition. A later Noema `409` cannot undo a Drive write that the app already performed without a Drive precondition.

## Native Google authorization

The app starts Google OAuth with its platform-native public client and PKCE/Google SDK support. Request `https://www.googleapis.com/auth/drive.appdata` only for Drive; do not request `drive` or `drive.file`. Identity scopes (`openid email profile`) may be returned by the Google SDK. Do not put a client secret in Flutter.

The app sends its Google ID token and short-lived Google access token to `POST /api/v1/google_drive/account/link`. Noema verifies both against Google's token-info service, checks audience, identity match and granted scopes, then discards both token values. They are never stored, returned, or written to Noema logs. The access token is sent to Google for verification only; it is not used as a Drive proxy. Refresh scope state after reauthorization, and call `POST /api/v1/google_drive/account/status/refresh` after a Drive authorization failure. An invalid/revoked access token marks the linked account `revoked`; transient Google verification failures do not change stored status.

Every request below, including account linking, requires `Authorization: Bearer <Noema access token>`. `GOOGLE_OAUTH_CLIENT_IDS` is the comma-separated set of public OAuth client IDs registered for Android, iOS, and any supported web client. The matching client audience is required for ID-token and access-token verification.

### Account status

`GET /api/v1/google_drive/account/status`

Unlinked response:

```json
{
  "account_id": null,
  "google_email": null,
  "state": "not_linked",
  "drive_appdata_granted": false,
  "sync_available": false,
  "granted_scopes": [],
  "checked_at": null,
  "error": "google_account_not_linked"
}
```

Linked response:

```json
{
  "account_id": "971235ac-66ed-4e27-8b5a-8d8a4c75361f",
  "google_email": "reader@example.com",
  "state": "granted",
  "drive_appdata_granted": true,
  "sync_available": true,
  "granted_scopes": [
    "https://www.googleapis.com/auth/drive.appdata",
    "openid"
  ],
  "checked_at": "2026-10-31T12:00:00Z",
  "error": null
}
```

`state` is `not_linked`, `granted`, `missing`, `revoked`, or `unknown`. A `missing` response uses `drive_appdata_scope_missing`; a revoked response uses `google_authorization_revoked`. The endpoint never returns OAuth credentials.

Missing Drive scope:

```json
{
  "account_id": "971235ac-66ed-4e27-8b5a-8d8a4c75361f",
  "google_email": "reader@example.com",
  "state": "missing",
  "drive_appdata_granted": false,
  "sync_available": false,
  "granted_scopes": ["openid", "email"],
  "checked_at": "2026-10-31T12:00:00Z",
  "error": "drive_appdata_scope_missing"
}
```

Revoked/invalidated authorization:

```json
{
  "account_id": "971235ac-66ed-4e27-8b5a-8d8a4c75361f",
  "google_email": "reader@example.com",
  "state": "revoked",
  "drive_appdata_granted": false,
  "sync_available": false,
  "granted_scopes": [],

  "error": "google_authorization_revoked"
}
```

### Link / refresh authorization state

`POST /api/v1/google_drive/account/link` and `POST /api/v1/google_drive/account/status/refresh` use the same body:

```json
{
  "google_id_token": "<short-lived Google ID token>",
  "google_access_token": "<short-lived Google access token>"
}
```

The successful response has the same shape as the linked account status above. Google Drive routes are limited to 120 requests per authenticated user per minute per API worker; OAuth link/refresh checks have a tighter 10-per-minute limit. Deployments with multiple workers should also apply a shared gateway/WAF rate limit.

### Backup metadata

`POST /api/v1/google_drive/backups` records metadata after the Flutter app has completed a direct Drive write. `idempotency_key` is required and must be reused unchanged for a retry of the same operation.
The backend stores a request fingerprint receipt atomically with the metadata mutation, so a replay remains idempotent even after a later metadata update. Reusing the key with a different request returns `409 idempotency_key_reused`. If metadata created by a POST was subsequently deleted, replaying that POST returns `409 backup_metadata_deleted` rather than recreating the deleted record. The legacy create route derives a stable key when one is omitted.

Metadata accepts only the listed scalar fields; tokens, passwords, prompts, notes, file payloads, and arbitrary nested values are rejected. `keep_local`, `keep_remote`, `merge`, and `duplicate` are client decisions only.

`error_details` is a safe error code, not a free-form message: `google_authorization_revoked`, `drive_appdata_scope_missing`, `drive_revision_conflict`, `drive_file_missing`, `drive_quota_exceeded`, `network_unavailable`, `snapshot_validation_failed`, `restore_failed`, or `unknown_error`.

## Snapshot category guidance

The backend repository does not contain the Flutter local persistence schema, so it cannot authoritatively enumerate app-local domain tables. Flutter should include only user-owned data that is genuinely local in its own schema, and version this category list with `schema_version`. Do not snapshot credentials, Google/Noema tokens, passwords, prompts, or server payloads that can be fetched again.

Known server-managed categories to exclude from a local snapshot:

- Noema account/authentication records and device registry.
- `user_global_config` and its `preferences`; these are already server-synced.
- The persisted `user_local_config` row is already server-managed and must not be copied as a portable/global preference category.
- Language catalog, server-managed color/typography theme records, and `response_language_preference_order`.
- Any other data already synchronized to the Noema database.

`user_local_config.preferences` and its selected language/theme overrides are device-bound. If Flutter includes an override for local recovery, keep it associated with its originating device/install; do not convert it into a global preference or silently restore it onto a different device. A product decision is needed in Flutter before portable cross-device restoration of these overrides.

Recommended manifest fields are `format`, `schema_version`, `snapshot_version`, `created_at`, `installation_id`, `included_categories`, `excluded_categories`, per-category `counts`, and per-category `hashes`. Keep manifest fields descriptive only; never put credentials, secrets, or snapshot content in the manifest.

## Google Cloud and deployment configuration

1. Enable the Google Drive API and configure the OAuth consent screen and applicable verification/test-user requirements for the app's audience.
2. Register public OAuth client IDs for each supported Android package/signing certificate and iOS bundle ID. Add a web client only if the product uses one. Use the platform SDK's native authorization-code/PKCE flow; no client secret belongs in Flutter.
3. Request only `https://www.googleapis.com/auth/drive.appdata` for Drive access. The old server-side `/auth/google/link` and callback are retired with HTTP 410.
4. Configure backend `GOOGLE_OAUTH_CLIENT_IDS` as a comma-separated list containing exactly those audiences. No Google client secret is needed by this backend flow.
5. Apply `migrations/20261031_google_drive_sync_metadata.sql` once against the PostgreSQL database before deploying the new API. It preserves backup/log rows, marks old OAuth state `unknown`, and clears old server-held OAuth token ciphertext because the native direct-transfer flow no longer uses it.

Existing environment requirements remain: database connection settings (`user`, `password`, `host`, `port`, `dbname`), Noema `secret_key` for JWTs, and the existing API encryption key for other modules that still use it. The Google Drive sync path introduces no new server secret. Reauthorize Google on-device after rollout; pre-migration Google grants may be revoked by the user in Google Account security settings.

The retired `GET /api/v1/auth/google/link`, `GET /api/v1/auth/google/callback`, and legacy Google account `POST /api/v1/auth/google/create` / `PUT /api/v1/auth/google/update/{id}` return `410 Gone`, for example `{"detail":{"code":"google_oauth_flow_retired","message":"Google account linking now uses the native app OAuth flow."}}`. The old create/update endpoints no longer accept token or scope fields.

The existing ownership-scoped `GET /api/v1/auth/google/get/{identifier}` remains read-only. Its `GoogleAccountOut` adds the current status fields and never contains token columns:

```json
{
  "id": "971235ac-66ed-4e27-8b5a-8d8a4c75361f",
```

## Password update

`POST /api/v1/user/create` also requires the same password rule. Example request:

```json
{
  "user_name": "reader",
  "primary_email": "reader@example.com",
  "user_display_name": "Reader",
  "password": "LocalPass1"
}
```

It returns `UserOut` (the same response shape shown below, with the server-created ID/timestamps and without a password field).

The existing `PUT /api/v1/user/update` route now enforces the app's password rule without trimming whitespace: at least 8 characters, one Unicode letter, and one digit. When changing a password, the authenticated request must also include the current password:

```json
{
  "current_password": "OldPass1",
  "password": "NewPass2"
}
```

Successful `200 OK` response (`UserOut`):

```json
{
  "id": "b08c5a73-2437-4e15-8a3c-d46e010f2367",
  "user_name": "reader",
  "primary_email": "reader@example.com",
  "user_display_name": "Reader",
  "created_at": "2026-10-01T10:00:00Z",
  "updated_at": "2026-10-31T12:20:00Z",
  "is_active": true,
  "is_verified": true
}
```

An incorrect current password returns `401`; an invalid new password returns `422`. Reset-by-email remains the existing reauthentication alternative and validates the same password rule before consuming its reset code. Password values are not written to application logs.
