# Google Drive synchronization contract

The canonical OpenAPI document is generated by FastAPI at `/openapi.json` (Swagger UI: `/docs`). This repository has no checked-in OpenAPI source or generated client; route and Pydantic declarations are the source of truth.

## Quick integration map

All paths below are relative to the API base URL `/api/v1`. Send the Noema JWT as `Authorization: Bearer <noema_access_token>` on every route, including account linking. Use the Google access token only for direct Google Drive API calls from Flutter; the Noema API does not provide Drive credentials.

| Purpose | Endpoint | Success |
|---|---|---|
| Read linked-account state | `GET /google_drive/account/status` | `200` |
| Link native Google authorization | `POST /google_drive/account/link` | `200` |
| Re-check current Google authorization | `POST /google_drive/account/status/refresh` | `200` |
| List backup metadata | `GET /google_drive/backups` | `200` |
| Get one backup metadata record | `GET /google_drive/backups/{backup_id}` | `200` |
| Record metadata after a direct Drive operation | `POST /google_drive/backups` | `201` |
| Update metadata with optimistic concurrency | `PUT /google_drive/backups/{backup_id}` | `200` |
| Delete Noema metadata only | `DELETE /google_drive/backups/{backup_id}` | `200` |
| Record a sync event/result | `POST /google_drive/sync_log/create` | `201` |
| Read/list sync events | `GET /google_drive/sync_log/get/{id}`, `GET /google_drive/sync_log/list` | `200` |

Typical Flutter sequence:

1. Sign in to Noema and keep the Noema JWT separate from Google credentials.
2. With the platform Google SDK, request the `drive.appdata` scope using the native public client and PKCE-supported flow. Keep Google tokens in platform-secure storage; never send a client secret to the app.
3. Send the Google ID token and current short-lived access token to `/google_drive/account/link`. Continue only when the response has `sync_available: true`; `missing` means the user must grant the Drive app-data scope.
4. Read Noema backup metadata and inspect the Drive `appDataFolder` directly from Flutter. Compare the Google Drive version and the Noema logical snapshot version; do not treat them as the same version.
5. Before replacing a Drive file, use a Drive-side conditional update where that Drive API operation supports one. After the direct Drive operation completes, create/update the corresponding Noema metadata using the same operation idempotency key on retry.
6. On conflict, refresh metadata and Drive state, ask the user to choose a strategy, then perform any keep/duplicate/merge/restore work locally. Record the chosen result in the sync log.
7. To remove a backup, delete the Drive file directly first, then delete its Noema metadata record. Deleting Noema metadata never deletes the Drive file.

## Transfer boundary

The Flutter app owns snapshot creation, validation, compression, optional encryption, hashing, direct Drive API upload/download, Drive-side conditional writes/deletes, version comparison, conflict prompts, merge, and local transactional restore. No Noema route accepts or returns backup bytes. The backend stores only app-declared, bounded metadata and safe synchronization events. A declared hash or size is not verified by Noema.

For direct Drive writes, the app must use the Drive API revision/ETag precondition (`If-Match` where supported) in addition to the Noema metadata precondition. A later Noema `409` cannot undo a Drive write that the app already performed without a Drive precondition.

## Native Google authorization

The app starts Google OAuth with its platform-native public client and PKCE-capable Google SDK flow. Request exactly `https://www.googleapis.com/auth/drive.appdata` for Drive; do not request `drive`, `drive.file`, or other Drive scopes. Identity scopes (`openid`, `email`, `profile`, or the equivalent userinfo scopes) may also be returned by the Google SDK. Do not put a client secret in Flutter.

The app sends its Google ID token and short-lived Google access token in the JSON body to `POST /api/v1/google_drive/account/link`. Noema verifies issuer, expiry, email verification, configured client audience, identity match, and granted scopes using Google's token-info service. Tokens are held only for verification: Noema does not persist or return them. Application HTTP-client logging removes the token query string when logging token-info requests; do not enable request-body or query-string logging for these routes in a gateway, proxy, APM, or hosting platform. The access token is sent to Google for verification only; it is not used as a Drive proxy. Refresh state after the app obtains a renewed grant and call `POST /api/v1/google_drive/account/status/refresh` after a Drive authorization failure. An invalid/revoked access token marks the linked account `revoked`; transient Google verification failures do not change stored status.

Every request below, including account linking, requires `Authorization: Bearer <Noema access token>`. `GOOGLE_OAUTH_CLIENT_IDS` is the comma-separated set of public OAuth client IDs registered for Android, iOS, and any supported web client. The matching client audience is required for ID-token and access-token verification.

### Link / refresh authorization state

`POST /api/v1/google_drive/account/link` and `POST /api/v1/google_drive/account/status/refresh` use the same body:

```json
{
  "google_id_token": "<short-lived Google ID token>",
  "google_access_token": "<short-lived Google access token>"
}
```

The successful response has the same shape as the linked account status above (the state can be `missing` if the user did not grant `drive.appdata`). Send the request over HTTPS and configure TLS at the deployment ingress; the application rejects unknown body fields and limits each token to 8,192 characters. Google Drive routes are limited to 120 requests per authenticated user per minute per API worker; OAuth link/refresh checks also have a tighter 10-per-minute limit. These limits are in-memory and per worker, not a distributed quota; deployments with multiple workers should apply a shared gateway/WAF rate limit.

The backend checks the ID-token audience and the access-token `issued_to`/`audience` against `GOOGLE_OAUTH_CLIENT_IDS`. Configure every legitimate platform client ID that can obtain a token and no unrelated client IDs. A Google account already linked to a different Noema user is not disclosed or transferred; the API responds with a generic conflict.

### Backup metadata

`POST /api/v1/google_drive/backups` records metadata after the Flutter app has completed a direct Drive write. `idempotency_key` is required and must be reused unchanged for a retry of the same operation.
The backend stores a request fingerprint receipt atomically with the metadata mutation, so a replay remains idempotent even after a later metadata update. Reusing the key with a different request returns `409 idempotency_key_reused`. If metadata created by a POST was subsequently deleted, replaying that POST returns `409 backup_metadata_deleted` rather than recreating the deleted record. The legacy create route derives a stable key when one is omitted.

```json
{
  "id_google_account": "971235ac-66ed-4e27-8b5a-8d8a4c75361f",
  "id_device": "39bb5203-46ed-442c-829c-714d10bfc3e5",
  "drive_file_id": "app-data-file-id",
  "local_ref": "primary-snapshot",
  "drive_version": "42",
  "snapshot_version": "17",
  "content_hash": "sha256:5c2d7f0bb5921471021c99efb2e357d5",
  "size_bytes": 84210,
  "operation_state": "completed",
  "idempotency_key": "37d19871-7e6a-4b1f-bcff-53dc0d397a44",
  "manifest": {
    "format": "noema-snapshot",
    "schema_version": 3,
    "snapshot_version": "17",
    "created_at": "2026-10-31T12:00:00Z",
    "installation_id": "install-7d2c",
    "included_categories": ["local_library"],
    "excluded_categories": ["account", "global_preferences"],
    "counts": {"local_library": 12},
    "hashes": {"local_library": "sha256:5c2d7f0bb5921471021c99efb2e357d5"}
  }
}
```

`drive_version` is the revision/version reported by Google Drive. `snapshot_version` is the app's logical snapshot version. `content_hash` and manifest hashes are client declarations, not server-verified. File size is bounded to 10 GiB; the manifest is bounded to 16 KiB. No user ID inside a manifest is an authorization signal.

The server validates these field limits before writing:

- `drive_file_id`: 1–255 characters; `drive_version`: 1–255; `snapshot_version`: 1–128; `content_hash`: at most 128 characters and a hexadecimal digest (optional short algorithm prefix, 16–128 hex characters).
- `size_bytes`: strict integer from 0 through 10 GiB; `local_ref`: at most 255 characters.
- `id_google_account` must belong to the authenticated user and currently have the `drive.appdata` grant. `id_device` is required on the new POST and must belong to that same Noema user. Unknown JSON fields are rejected.
- `operation_state`: `pending`, `completed`, or `failed`. The API records the app-reported state; it does not independently verify the Drive operation.
- The manifest fields are required for new POSTs: `format` (1–64 safe characters), `schema_version` (positive integer), `snapshot_version`, `created_at`, `installation_id`, `included_categories`, `excluded_categories`, `counts`, and `hashes`. Category lists have at most 64 unique safe names each; `counts` and `hashes` have at most 100 entries; count values are non-negative integers. Count/hash keys must refer to included categories, and a category cannot be both included and excluded. All manifest JSON together is limited to 16 KiB.

The JSON body schemas for account linking, backup create/update, and sync-log creation reject additional properties. Use UTC ISO-8601 timestamps. The account ID, device ID, and backup ID are references only: ownership is checked from the authenticated Noema user, never inferred from IDs in the manifest.

`GET /api/v1/google_drive/backups?limit=100&offset=0` lists only the authenticated user's metadata and returns an array of the complete `BackupFileOut` object above (`[]` when empty). `GET /api/v1/google_drive/backups/{backup_id}` returns that same object for one owned record.

`DELETE /api/v1/google_drive/backups/{backup_id}` returns `{"deleted":true,"drive_file_deleted":false}`. It removes only the Noema metadata row. The app deletes a Drive object directly and then removes the metadata.

The DELETE operation is ownership-scoped and returns `404` for missing or foreign records. If the user wants to unlink/switch Google accounts, first delete all metadata rows tied to the old account, then use the existing `DELETE /api/v1/auth/google/delete/{id}` route for that owned account; this route also only unlinks Noema and never deletes Drive files. Unlink returns `409 google_account_has_backups` while backup metadata still references the account, so those rows cannot accidentally be associated with a different Google identity. Link does not silently replace a different account.

The established `/api/v1/google_drive/backup_file/get/{id}`, `/backup_file/list`, `/backup_file/create`, and `/backup_file/delete/{id}` paths remain as compatibility routes. Reads use the same ownership filters and `BackupFileOut`; delete now explicitly returns `{"deleted":true,"drive_file_deleted":false}`. Legacy create accepts its original fields plus optional `id_device`, `snapshot_version`, `size_bytes`, `operation_state`, `manifest`, and `idempotency_key`; when omitted, it derives a stable idempotency key from the legacy request. New clients should use `/backups`, which requires the full manifest, device, operation state, and idempotency key.

`GET /api/v1/google_drive/sync_log/get/{id}` returns one such object; `/sync_log/list` returns an array of them. Metadata accepts only the listed scalar fields; tokens, passwords, prompts, notes, file payloads, and arbitrary nested values are rejected. `keep_local`, `keep_remote`, `merge`, and `duplicate` are client decisions only.

`error_details` is a safe error code, not a free-form message: `google_authorization_revoked`, `drive_appdata_scope_missing`, `drive_revision_conflict`, `drive_file_missing`, `drive_quota_exceeded`, `network_unavailable`, `snapshot_validation_failed`, `restore_failed`, or `unknown_error`.

The accepted events are `sync_started`, `sync_completed`, `sync_failed`, `conflict_detected`, `authorization_refreshed`, `backup_created`, `backup_updated`, and `backup_deleted`. `derection` accepts `upload` or `download`; clients may send the correctly spelled alias `direction`, but responses preserve the published `derection` field. `result` is `success`, `failure`, or `in_conflict`; `conflict_strategy` is nullable and otherwise one of `keep_local`, `keep_remote`, `merge`, or `duplicate`.

The optional `idempotency_key` is 16–128 characters; callers should supply one for retry safety. Replaying a matching log request returns the existing log (the route continues to respond `201`); reusing its key for different log data returns `409 sync_log_conflict`. `metadata` may contain only these scalar keys: `snapshot_version`, `drive_revision`, `content_hash`, `file_size_bytes`, `installation_id`, and `operation_id`. `file_size_bytes` must be an integer within the backup-size limit; other values must be safe strings up to 128 characters. Do not send free-form errors or any note, prompt, credential, user content, payload, or nested object. Sync-log list filters support `id`, `id_device`, `id_backup_file`, `id_google_account`, `event`, `derection`/`direction`, `result`, and `conflict_strategy`; pagination matches the backup list.

## HTTP errors and client handling

| Status | Meaning / expected client action |
|---|---|
| `401` | Noema JWT invalid/expired, Google ID token invalid, or the Google grant is invalid/revoked. Reauthenticate with the relevant provider; do not retry an unchanged invalid token indefinitely. |
| `403` | Google grant contains a disallowed scope. Reauthorize requesting only `drive.appdata` plus supported identity scopes. |
| `404` | Resource not found or not owned by the authenticated user. Treat foreign IDs as unavailable; do not try to enumerate them. |
| `409` | Drive scope unavailable, idempotency key reused, metadata changed, or database uniqueness conflict. Inspect `detail.code`; for `backup_version_conflict`, use `detail.current`, reload Drive state and ask the user before choosing a conflict strategy. |
| `422` | Invalid field, enum, filter, manifest, or request shape. Correct the request; do not automatically retry unchanged input. |
| `429` | Per-worker request limit. Respect `Retry-After`; deployments should also enforce a distributed limit at the gateway. |
| `502` / `503` | Google verification temporarily unavailable / Google OAuth configuration or backend dependency unavailable. Retry with bounded exponential backoff; these are not success responses. |

Error responses use FastAPI's standard envelope, usually `{"detail":{"code":"...","message":"..."}}`; validation errors (`422`) use FastAPI's validation detail. A version conflict returns the complete current metadata object as `detail.current`. A `409` response never means a Drive file was rolled back.

## Snapshot category guidance

The backend repository does not contain the Flutter local persistence schema, so it cannot authoritatively enumerate app-local domain tables. Flutter should include only user-owned data that is genuinely local in its own schema, and version this category list with `schema_version`. Do not snapshot credentials, Google/Noema tokens, passwords, prompts, or server payloads that can be fetched again.

Known server-managed categories to exclude from a local snapshot:

- Noema account/authentication records and device registry.
- `user_global_config` and its `preferences`; these are already server-synced.
- The persisted `user_local_config` row is already server-managed and must not be copied as a portable/global preference category.
- Language catalog, server-managed color/typography theme records, and `response_language_preference_order`.
- Any other data already synchronized to the Noema database.

`user_local_config.preferences` and its selected language/theme overrides are device-bound. If Flutter includes an override for local recovery, keep it associated with its originating device/install; do not convert it into a global preference or silently restore it onto a different device. A product decision is needed in Flutter before portable cross-device restoration of these overrides.

Recommended manifest fields are `format`, `schema_version`, `snapshot_version`, `created_at`, `installation_id`, `included_categories`, `excluded_categories`, per-category `counts`, and per-category `hashes`. Keep manifest fields descriptive only; never put credentials, secrets, or snapshot content in the manifest.

## Google Cloud and deployment configuration

1. Enable the Google Drive API and configure the OAuth consent screen and applicable verification/test-user requirements for the app's audience.
2. Register public OAuth client IDs for each supported Android package/signing certificate and iOS bundle ID. Add a web client only if the product uses one. Use the platform SDK's native authorization-code/PKCE flow; no client secret belongs in Flutter.
3. Request only `https://www.googleapis.com/auth/drive.appdata` for Drive access. The old server-side `/auth/google/link` and callback are retired with HTTP 410.
4. Configure backend `GOOGLE_OAUTH_CLIENT_IDS` as a comma-separated list containing exactly those audiences. No Google client secret is needed by this backend flow.
5. Take and verify a restorable PostgreSQL backup before migration. Apply `migrations/20261031_google_drive_sync_metadata.sql` against the PostgreSQL database **before** deploying the new API or enabling Drive sync. Run it through the deployment's approved secret-safe migration process, for example `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/20261031_google_drive_sync_metadata.sql`. It preserves backup/log rows, marks old OAuth state `unknown`, and clears old server-held OAuth token ciphertext because the native direct-transfer flow no longer uses it. Treat this as a one-way credential cleanup; the migration has no reverse script that restores those credentials. Verify the migration before API rollout:

   ```sql
   SELECT
       to_regclass('app_auth.google_account') IS NOT NULL
           AND EXISTS (
               SELECT 1 FROM information_schema.columns
               WHERE table_schema = 'app_auth'
                 AND table_name = 'google_account'
                 AND column_name = 'drive_appdata_status'
           )
           AND to_regclass('google_drive.backup_operation_idempotency') IS NOT NULL
           AS google_drive_sync_schema_ready;
   ```

   The result must be `true`. If the application has already been deployed and returns `UndefinedColumn` for `drive_appdata_status`, apply the migration immediately, verify readiness, then retry the request. The legacy `GET /api/v1/auth/google/get/{identificator}` temporarily remains usable before migration and reports Drive state as `unknown`; after migration it returns the persisted state. The new Drive sync endpoints require the migration.

Existing environment requirements remain: database connection settings (`user`, `password`, `host`, `port`, `dbname`), Noema `secret_key` for JWTs, and the existing API encryption key for other modules that still use it. The Google Drive sync path introduces no new server secret. Reauthorize Google on-device after rollout; pre-migration Google grants may be revoked by the user in Google Account security settings.

The retired `GET /api/v1/auth/google/link` and `/api/v1/auth/google/callback` return `410 Gone` with `code: "google_oauth_flow_retired"`. Legacy Google account `POST /api/v1/auth/google/create` and `PUT /api/v1/auth/google/update/{id}` also return `410 Gone`, with `code: "google_account_write_flow_retired"`; these routes no longer accept token or scope fields. All are replaced by native linking at `/api/v1/google_drive/account/link`.

The existing ownership-scoped `GET /api/v1/auth/google/get/{identifier}` remains read-only. Its `GoogleAccountOut` adds the current status fields and never contains token columns:

## Password update

`POST /api/v1/user/create` also requires the same password rule. Example request:

```json
{
  "user_name": "reader",
  "primary_email": "reader@example.com",
  "user_display_name": "Reader",
  "password": "LocalPass1"
}
```

It returns `UserOut` (the same response shape shown below, with the server-created ID/timestamps and without a password field).

The existing `PUT /api/v1/user/update` route now enforces the app's password rule without trimming whitespace: at least 8 characters, one Unicode letter, and one digit. When changing a password, the authenticated request must also include the current password:

```json
{
  "current_password": "OldPass1",
  "password": "NewPass2"
}
```

Successful `200 OK` response (`UserOut`):

```json
{
  "id": "b08c5a73-2437-4e15-8a3c-d46e010f2367",
  "user_name": "reader",
  "primary_email": "reader@example.com",
  "user_display_name": "Reader",
  "created_at": "2026-10-01T10:00:00Z",
  "updated_at": "2026-10-31T12:20:00Z",
  "is_active": true,
  "is_verified": true
}
```

An incorrect current password returns `401`; an invalid new password returns `422`. Reset-by-email remains the existing reauthentication alternative and validates the same password rule before consuming its reset code. Password values are not written to application logs.
